\begin{abstract}
Autonomous AI agents need the web to support both information retrieval and automated action. This study evaluates public web readiness by analyzing 50,000 domains sampled across the top one million global websites from the research-backed Tranco popularity ranking through 61 automated checks using direct HTTP requests without logins or client-side JavaScript. Basic homepage text was accessible on 45.71\% of domains without requiring a browser to run scripts. When evaluating whether sites provide readable content while simultaneously allowing automated access, on 30.16\% of all domains, the text rule passed and both requests using the crawler names GPTBot and PerplexityBot were recorded as HTTP 200 (``OK'') without being blocked by anti-bot firewalls. Established discovery signals were relatively common, with sitemaps and robots-file markers and machine-readable page metadata (JSON-LD) passed on 27.37\% and 21.37\%, respectively. Dedicated agent infrastructure remains rare, as at least one check for specialized guidance files, Markdown negotiation, or Model Context Protocol (MCP) endpoints passed on 7.50\% of domains, and candidate API descriptions passed on 0.16\% with an OpenAPI version marker. While agents can retrieve static text from parts of the web, structured public interfaces for autonomous action remain rare.

\par\medskip
\noindent{\small \textit{Keywords:} AI agents, agent readiness, web measurement, robots.txt, llms.txt, Model Context Protocol, OpenAPI, Tranco, CrUX}

\end{abstract}

\section{Introduction}

AI agents are software systems in which an AI model chooses actions and uses tools to work toward a user's goal. Those tools can include a web browser, a search service, or an application programming interface (API), which lets software request data or operations from another service. An agent can use the result of one action to decide what to do next \cite{ref31}. For example, it may search for product information, compare alternatives, or complete an online form.

In July 2025, OpenAI introduced ChatGPT agent with tools for browsing websites and using APIs \cite{ref32}. Such products make website readiness a practical question for users and developers. A user can ask an agent to complete a task, but the agent still needs to find the right information and a way to use the relevant service.

For an AI agent to execute tasks autonomously, a website must support two distinct capabilities, information retrieval and service execution. Today, these capabilities are split. Human-facing websites often publish rich informational text but lack machine-readable API specifications, forcing agents to rely on expensive visual browsing or fragile HTML scrapers. Conversely, software services frequently provide structured APIs but hide them behind authentication or omit machine-discoverable documentation from their public homepages.

Because full browser emulation carries high computational latency and cost, many agent architectures rely on lightweight, direct HTTP requests to locate resources. For an agent to gather information, a website must satisfy two basic conditions, it must return readable text directly without requiring browser JavaScript execution, and its network firewalls must not block automated requests. While 45.71\% of domains returned readable HTML text, only 30.16\% simultaneously allowed test requests carrying common AI agent identifiers (GPTBot and PerplexityBot) through without blocking them. This raises a fundamental empirical question of how much of the existing public web an autonomous agent can understand and use through standard HTTP requests alone, without relying on client-side JavaScript execution or authenticated credentials.

This analysis asks how often the selected rules match, how their matches overlap, and how the results depend on site rank and collection procedure. It combines complete check counts with rank-adjusted estimates, paired repeat-scan comparisons, and tests with prepared responses. The contribution is a reproducible description of these public-web signals and the limits on interpreting them as readiness; completed agent tasks were not part of the scan.

\section{Related Work}

Research on AI agents usually tests whether models can finish specific tasks. For example, WebArena measures whether an agent can book a flight, post on a forum, or buy an item on simulated websites \cite{ref33}. Those benchmarks test the model's problem-solving skills inside controlled environments. In contrast, this study does not measure model skill or task completion. It checks whether real, public websites provide the basic text, files, and interfaces that an agent needs to work autonomously.

Existing web measurement projects analyze frontend technologies and performance, but they do not examine whether sites support automated software. For example, the HTTP Archive tracks CMS platforms, JavaScript libraries, page weight, and loading times designed for human browsing \cite{ref21}. Studies looking at newer agent formats show that a successful server reply does not mean the file is valid. When Thunderbit looked for llms.txt files across 10,000 domains, 1,606 addresses returned an HTTP 200 code, but only 586 actually contained valid files \cite{ref22}. The other servers returned ordinary HTML web pages, error messages, or redirects. An agent cannot assume a file exists just because an address responds.

Other studies inspect robots.txt files to see what websites allow automated crawlers to do \cite{ref23,ref24,ref25}. However, what a website writes in robots.txt does not guarantee what its servers allow in practice. Security systems and firewalls often block automated visitors even when robots.txt allows them. For this reason, this study checks both the written rules in robots.txt and sends test requests using crawler names such as GPTBot and PerplexityBot to see if the server lets them through.

Publishing these files also does not mean agents use them. An analysis by Ahrefs of 137,210 domains found that 97\% of detected llms.txt files received no requests at all in May 2026 \cite{ref26}. In commercial tooling, Ora's methodology page lists 126 checks across four groups as of October 2026 \cite{ref29}. Because different studies use different websites and scoring rules, their numbers cannot be compared directly. This study uses a clear, open set of 61 automated checks to measure basic access, resource discovery, and service interfaces across 50,000 domains.

\section{Study Design}

Evaluating agent readiness requires looking at how automated software actually interacts with web infrastructure. This study organizes its 61 checks into three primary operational areas. Access checks verify whether homepages return standard response codes and readable text without requiring browser rendering. Discovery checks scan for sitemaps, crawler permissions, and machine guidance files that tell agents where resources reside. Service interface checks probe for structured API specifications, protocol endpoints, and authentication guidelines needed for execution.

Because different agents require different tools, a single pass mark cannot describe readiness. A research agent searching for articles only needs readable text and clear sitemaps, while a purchasing agent requires structured API endpoints and transaction support; optional files such as llms.txt are not requirements for all tasks. This study records each signal independently, establishing where public web infrastructure supports autonomous software and where gaps remain.

\subsection{Sample}

The sampling frame comes from the Tranco ranking, an established scientific benchmark that measures website popularity by combining multiple web traffic providers (such as Cisco Umbrella, Alexa, and Majestic) over a 30-day window to filter out transient spikes and manipulation \cite{ref1,ref27,ref28}. This study uses the top one million global domains from Tranco list ZJQ6G, generated on 2 September 2026.

The sample includes every domain ranked 1 through 10,000. From each of the next two rank groups, it includes 20,000 domains picked at random, with no domain picked twice. The random seed is 20260903, allowing the same selection to be reproduced.

\subsection{Why these 61 checks}

The checklist inspects public pages, standard files, and HTTP response headers. These signals reflect what automated agents need at different stages of a task \cite{ref31}. Basic access tests verify whether pages return readable text. Discovery checks identify sitemaps, crawler permissions, and machine guidance files. Interface checks look for API descriptions, protocol endpoints, and authentication rules. General metadata and security headers provide operational context, while payment signals matter for commercial interactions.

All checks evaluate public URLs and server responses without logging into user accounts, running browser JavaScript, filling forms, or completing transactions. This provides an objective baseline for comparing websites across the web, though it does not test private or interactive workflows. The checklist originated from merging an early AI-standards list with general web quality checks, later expanding to cover AI search, autonomous agents, and structured metadata.

The 61 checks represent an exploratory inventory rather than a definitive standard for agent readiness. Grouping choices affect the total count; for example, verifying an MCP server and checking its capabilities count as two separate checks, whereas testing two crawler user-agents produces one combined check. While these checks capture useful signals, passing more checks does not prove that an AI agent will succeed at a given task.

\subsubsection{Requests and matching rules}

The scanner implementation begins with 34 fetch requests per domain and can check up to six additional resources if initial probes succeed. Following HTTP redirects can increase this request count. The probes target the homepage over HTTPS alongside well-known paths such as /robots.txt, /llms.txt, and /openapi.json, with a 4.5-second timeout per operation. One homepage request requests Markdown or plain text. Two other requests test User-Agent headers for GPTBot and PerplexityBot. The scanner does not run client-side JavaScript or log in. Appendix B provides the complete matching rules.

The text check evaluates the standard homepage response, falling back to the Markdown response if the standard page is empty. It strips scripts, stylesheets, and HTML tags, requiring more than 300 characters of text to pass. Error pages and hidden text can still satisfy this count.

The crawler check records whether both, one, or neither of the test requests return an HTTP 200 response. The MCP check tests two candidate service paths with a JSON-RPC initialization payload, passing if the server returns an HTTP status between 200 and 299 with the string jsonrpc. A second check parses the response as JSON and looks for an explicit capabilities object.

\subsection{Saved results and repeat scans}

Each saved domain record contains 61 check labels, an overall score, category scores, the scan timestamp, and the duration in milliseconds. The four possible labels are pass, warning, fail, and not applicable. A warning indicates a partial match or an unverified signal, while not applicable marks an optional feature that was absent or dependent on another prerequisite check. Appendix C explains the scoring formulas and rank weighting.

The dataset contains one record for each of the 50,000 sampled domains, collected over 18.77 hours on September 3-4, 2026 UTC. To address transient network drops, the collection pipeline automatically rescanned 21,547 domains whose initial score was 10 or below, replacing earlier records with new results.

\subsection{Tests with prepared responses}

To test the scanner's matching rules, the implementation was evaluated against 13 prepared test cases with known responses, including empty replies, server errors, and standard HTML pages. Because the true inputs were known, these tests revealed where heuristic rules can produce false passes or misinterpret server errors.

\subsection{Comparisons}

The analysis investigates several key patterns across the 50,000 domains.

First, it examines the joint adoption of three emerging agent technologies, llms.txt files, Markdown content negotiation, and Model Context Protocol (MCP) endpoints, counting how often domains implement none, one, two, or all three standards.

Second, it evaluates practical access by measuring how often domains return readable homepage text while simultaneously allowing automated crawlers through with HTTP 200 responses.

Third, it compares domains listed in Chrome's User Experience Report (CrUX) against unlisted domains, standardizing both groups to identical rank distributions to determine whether higher pass rates reflect site popularity or structural differences.

Finally, it compares paired repeat scans among low-scoring domains to determine how network retries affect overall scores.

\subsection{Content access and request outcomes}

For an AI agent to read a website without a full browser, two basic conditions must be met. First, the website must return readable text directly in its raw HTML without requiring browser JavaScript execution. Second, web security firewalls must not block automated requests.

In this study, the text-length check evaluates whether a website provides at least 300 characters of readable plain text directly on its homepage. This check passed on 22,855 domains (45.71\%) and failed on 27,145 (54.29\%), where pages were blank, required JavaScript rendering, or returned connection errors. 

To evaluate whether web firewalls block automated agents, the scanner sent test requests identifying themselves as AI crawlers using the User-Agent headers for GPTBot (OpenAI) and PerplexityBot. Among domains passing the text check, both crawler-named requests returned HTTP 200 on 65.98\%, one on 11.28\%, and neither on 22.74\%. The average checklist score in this group was 41.1.

Both conditions, readable text and unblocked access for both AI crawlers, occur on 15,080 domains, or 30.16\% of the full sample. Requiring both conditions gives fewer matches than checking either alone. Because the text check only counts total characters rather than understanding meaning, a website returning a verbose 500-word error screen (such as an access-denied page) will pass the check, whereas a working website with a concise homepage under 300 characters will fail it.

Domains failing the text check still produced positive results on other checks. For example, 452 passed the llms.txt check and 2,231 passed the sitemap-and-robots check. Table 5 reports counts and percentages within each group; a domain can appear in several rows.

\subsection{Where the checks can mislead}

Automated checks rely on simple heuristics, which can sometimes produce misleading results when servers behave unexpectedly. For example, returning the same generic HTML page for every requested address produced 23 passes and an artificial score of 47. A verbose HTTP 403 (``Forbidden'') error page passed the text check because it contained over 300 characters of error text, while a working static page with concise text failed it.

\subsection{How repeat scans affect the comparison}

\subsection{Reading and discovering information}

Because websites format information differently, automated agents benefit from exploring multiple discovery paths, such as standard pages, XML sitemaps, structured JSON-LD data, or llms.txt files. 

Most MCP server detections occur on domains that also provide llms.txt and Markdown responses. This clustering suggests that early adopters often deploy multiple AI standards at once. However, checking homepage text alone is not a reliable filter for whether a site provides machine resources. A domain with minimal homepage text can still host working APIs at other addresses, while a website serving a verbose error page can mistakenly pass the text check simply because the error message contains hundreds of words. Each resource requires independent inspection.

\subsection{Moving from information to action}

The low match rates for MCP (1.82\%) and OpenAPI (0.16\%) reflect the limits of probing fixed default paths without client-side script rendering. A service may host an API at an unprobed address or require authentication before revealing its endpoints.

Furthermore, detecting an endpoint marker does not prove that an agent can execute an action. Server responses wrapped in Server-Sent Events can cause simple parser checks to fail even when the underlying service is fully functional. Positive and negative checks indicate whether responses matched specific heuristic patterns, not whether an agent could complete a live task.

\subsection{Practical priorities for websites and agents}

For website operators wishing to support autonomous software, ensuring that pages return clean text without mandatory JavaScript rendering, publishing XML sitemaps, and providing clear API documentation offer the most immediate benefits. 

For agent developers, verifying file contents is essential. As shown by Thunderbit, many HTTP 200 responses to llms.txt paths return regular web pages rather than markdown guidance. Agents must verify response structure rather than assuming success from HTTP status codes alone.

A rigorous next step would be evaluating agent task success across domains that pass versus fail these infrastructure checks, testing whether these static indicators predict practical task completion.

\section{Limitations}

This study evaluates recorded check results rather than complete task executions. The saved records store categorical labels (pass, warning, fail, not applicable) rather than full HTTP response bodies, exact error traces, or redirect chains. This prevents retrospectively testing alternative text thresholds or diagnosing network timeout causes.

The checklist weights various indicators, but individual checks do not matter equally for every task. A research agent only requires readable text and sitemaps, while a transaction agent requires APIs and payment flows. The study does not establish that higher scores increase task completion rates.

Additionally, measurements reflect the specific request headers, paths, timeouts, and single-attempt retry rules used during collection. Crawler test requests used identifiable User-Agent strings but do not reflect full crawler behavior. Finally, private corporate intranets, authenticated services, and pages requiring interactive browser rendering lie entirely outside this study's scope.

\section{Conclusion}

This study measures the public web's readiness for autonomous AI agents across 50,000 domains sampled from the Tranco top one million. The text check passes on 45.71\% of domains. Across all domains, 30.16\% pass that check and receive HTTP 200 for both crawler-named requests. At least one of the three checks for llms.txt, Markdown, and a basic MCP marker passes on 7.50\% of domains. These are recorded check results, not a validated readiness grade for the web.

Dedicated machine interfaces remain rare on the public web, with basic MCP and OpenAPI markers on 1.82\% and 0.16\%, respectively, at the tested addresses. The study did not execute complete tasks. Its practical contribution is a reproducible baseline of access, discovery, and interface readiness across the global web, showing that while agents can read static information from many sites, structured public infrastructure for automated service interaction remains rare.

\subsection*{B.7 Response selection}

Text checks use the ordinary homepage reply if its body contains any characters. Otherwise, they use the Markdown reply, or empty text if neither has content. Several header checks use the first available header set in this order, ordinary homepage, Markdown request, then GPTBot request. The program makes these choices without requiring a successful response code. Text and header checks can therefore read different replies.

The text rule removes scripts, styles, and tags using text patterns, then reduces repeated spaces and line breaks. It uses JavaScript's string length, measured in UTF-16 code units, so some characters count as two. Hidden text also counts, and a written HTML code such as \&amp; stays encoded rather than becoming one displayed character. Failed requests give the checks no response object, and failures while reading a reply give them empty text.

\subsection*{B.8 Request settings}

The rules follow \href{https://github.com/vedangvatsa/vedang-website/commit/ea0e797ecc13e494968500db03f128679f05b92b}{scanner revision ea0e797}. That version predates the saved results and uses the same check names and record format.

Most requests use VedaAgenticScanner/1.0 (+https://veda.ng/scan; agent-readiness-audit). The Markdown root request adds Accept: text/markdown, text/plain;q=0.9. The two bot root requests use Mozilla/5.0 (compatible; GPTBot/1.0; +https://openai.com/gptbot) and Mozilla/5.0 (compatible; PerplexityBot/1.0; +https://perplexity.ai/perplexitybot).

MCP requests use POST and Content-Type: application/json. Their JSON-RPC 2.0 initialize payloads specify protocol version 2024-11-05, empty capabilities, and client name veda-scanner version 1.0. Request IDs are probe-1 and probe-2. The implementation stops after the response and lacks the Accept-header and event-stream handling required by the later Streamable HTTP transport \cite{ref30}.

The program follows redirects. It does not separately try adding www or changing HTTPS to HTTP. A sitemap or feed link can lead to another host, but the result still counts under the starting domain. Requests do not log in. The program fetches robots.txt alongside the other resources instead of checking its rules before making requests. It does not submit forms, make payments, or keep cookies between requests. The \href{https://github.com/vedangvatsa/vedang-website/blob/af35d3c49de6f8a9b8352d334875db748cae7d8f/scripts/scan-watchdog.sh}{watchdog} allows three domains to be processed at once in each process and can run several processes.

\section*{Appendix C. Scores and Sampling Weights}

\subsection*{C.1 Checklist score}

The program compares the points earned with the maximum points from checks it marks neither optional nor not applicable. It expresses the result as a percentage, rounds to a whole number, and caps it at 100. Optional checks can add points without increasing the maximum used in this calculation. If that maximum is zero, the program uses one instead.

Two results with the same label can earn different points, so this paper uses the scores saved by the program. The input-HTTPS rule adds three points per domain. Category scores use the same method. Their averages are 41.0 for security, 28.9 for metadata, 23.9 for access, 20.7 for discovery, 9.8 for payments, and 7.4 for interfaces.

Optional points can increase the score without increasing its denominator, while applicability changes which checks enter that denominator. Equal scores therefore need not represent equal sets of passed checks or equal capabilities. The score comparisons describe the retained scoring system; the individual labels carry the more specific observations.

\subsection*{C.2 Why the results are weighted}

The sample gives highly ranked domains a larger share than they have in the full Tranco list \cite{ref1}. Weighting means giving each rank group its share of that full list when combining the results. The top 10,000 contribute 1\%, the next 90,000 contribute 9\%, and the remaining 900,000 contribute 90\%. These figures estimate outcomes under the same collection procedure for the full list, assuming comparable measurement conditions. They do not estimate all websites or remove the effect of selective rechecking. The separate CrUX comparison in Section 3.5 gives listed and unlisted domains the same chosen mix of ranks.

The bracketed 95\% ranges use a normal approximation with a correction for the share of each rank group sampled. They describe uncertainty from sampling only some domains in the lower two groups. All top-10,000 domains were included, so there is no sampling uncertainty for that group. These are separate ranges for each measure, conditional on the saved labels. They do not include request variability, mistaken matches, or uncertainty about repeat scans, and do not provide a combined test across the checklist. The analysis code gives the detailed calculations.
